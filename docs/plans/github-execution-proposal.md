## 1. 추천 방식

GitHub를 요구·승인·작업·검증의 기준으로 삼고, Codex가 미완료 작업을 읽어 실행한다.
Actions는 검사를 실행하고, Buzz는 연구·협의·운영 알림을 담당한다.
거래 실행 서비스와 개발 에이전트를 분리한다. 개발 중인 코드는 실계좌에 바로 연결하지 않는다.
승인된 개발 범위 안에서는 자율 진행하고 중요한 운용 전환에서 사용자에게 결과를 제시한다.
P0~P4 개발과 P5 모의 검증은 위임 승인되었다. P6 결과 수용과 P7 실거래 시작은 별도 결정이다.

| 후보 | 장점 | 한계 | 판단 |
| --- | --- | --- | --- |
| 매 작업 승인 | 직접 통제가 쉽다 | 작은 수정도 대기 발생 | 고위험 변경에 한정 |
| GitHub 기록 + Codex 단계 실행 | 중단 후 재개, 기존 환경·프록시 활용 | 세션 종료 후 무인 실행은 별도 장치 필요 | 초기 추천 |
| Actions에서 모든 개발 실행 | 이벤트 기반 실행 | 사설망·인증·장시간 작업·공개 PR 격리가 복잡 | CI에 한정 |
| 무인 개발 서비스부터 구축 | 정기 재개 가능 | 감독 시스템 자체의 개발·운영 필요 | 기본 흐름 검증 후 별도 제안 |

Project는 기록을 보여주는 화면이다. 카드 이동만으로 승인이나 완료가 생기지 않는다.
main은 승인된 기준, 열린 PR은 검토 중 제안이다. 미승인 PR을 실행 규칙으로 적용하지 않는다.
Wiki·Discussion에는 기준 문서를 연결하고 같은 설계를 복제하지 않는다.

## 4. 작업 하나의 실행 순환

1. 원격 main SHA, 현재 단계 이슈, 열린 PR, 최신 승인 범위를 읽는다.
2. 선행 작업이 통과한 승인 범위 내 작업 하나를 선택한다.
3. 작업 이슈에 목적·파일 범위·완료 조건·검사·선행 조건을 고정한다.
4. 승인된 main에서 branch를 만들고 구현한다. 사용자의 미커밋 변경을 보존한다.
5. 관련 검사를 실행한다. 버그 수정에는 재현과 회귀 검사를 포함한다.
6. 작업 경계에서 Fable 5.2로 한 번 리뷰하고 근거 있는 지적을 반영한다.
7. 수정 부분을 재검증하고 최종 commit SHA의 CI 결과를 확인한다.
8. PR에 변경·검사·리뷰·미검증을 기록한다. 승인된 통합 범위와 검사를 만족해야 merge한다.
9. remote main SHA와 통합 후 검사 결과를 확인하고 이슈·Project·STATE를 갱신한다.
10. 단계 기준 충족 시 결과 보고서를 만들고 직접 수용 또는 명시적 위임 수용에 따라 다음 단계로 간다.

CI 실패나 핵심 리뷰 지적이 남은 PR은 다음 단계의 입력으로 승격하지 않는다.
AI 리뷰를 같은 GitHub 계정의 인간 승인 리뷰로 표시하지 않는다.
개인 저장소에서 다른 사람의 필수 승인을 무조건 설정하면 통합이 막힐 수 있으므로 실제 reviewer 구성에 맞춘다.

## 5. 승인 방식

추천은 B다. 단순한 동의를 실계좌 운용 승인으로 확대하지 않는다.

| 방식 | 실행 | 사용자 검토 |
| --- | --- | --- |
| A. 단계별 직접 수용 | 각 단계 실행 후 대기 | 단계 결과마다 |
| B. 개발 범위 위임 | 고정된 P0~P4를 검증하며 순차 개발, P5 모의 관찰 | 설계 확정·범위 변경·P5 결과·실거래 전환 |

B 승인 범위는 개발 이슈·branch·테스트·Fable 리뷰·PR·검사 통과 후 merge·기록 갱신이다.
P0는 남은 설계 리뷰와 전제 확인을 포함한다. P0 미완료 상태에서 종속 P1을 시작하지 않는다.
P5는 모의·shadow만 허용한다. 운영 서버·인증 경로가 확정되어야 배포한다.
유료 계약, 보안 권한 확대, 기존 외부 서비스 설정 변경은 구체적 승인 범위가 없으면 제외한다.
P6 준비·복구 훈련은 P5 결과 수용 후 진행한다. P7은 대상 버전·계좌·한도·기간·정지 조건에 대한 별도 결정이 필요하다.

승인에는 제안 버전, 실제 답변·출처·시각, 허용 단계, 통합·배포 범위와 제외 범위를 남긴다.
모델·권한·비용·완료 기준 변경 시 영향 범위만 재검토한다. 범위 안 일상 수정은 재승인하지 않는다.
에이전트가 전사한 사용자 답변과 사용자가 GitHub에 직접 작성한 답변을 구분한다.
위임받은 완료 판정은 `위임 수용`이며 `사용자 직접 승인`이 아니다.
자동 승인 검사 도입 전에는 오래된 승인·다른 단계 승인·보류 이후 불일치 답변의 거부를 검증한다.
승인 도구의 종료코드만으로 사용자 의사나 제품 성공을 판정하지 않는다.

## 6. 단계별 산출물

| 단계 | 범위 | 보여줄 결과 | 다음 조건 |
| --- | --- | --- | --- |
| P0 | 설계·실행 방식, 남은 리뷰, 최소 CI·기록 설정 | 승인 범위·작업 지도·Fable 응답 | 설계·환경 전제 확인 |
| P1 | 한국투자증권·프록시 읽기 전용 연결 | 실제 데이터와 요청/반환 모델 | 주문 0·조회 성공·실패 구분 |
| P2 | 관심 종목·저장·재생·품질 | 누락·역순·달력·재생 결과 | 시점 누출·식별 오류 해소 |
| P3 | 기준 전략·비용·표본 외 평가·확률 | 성과와 불확실성, 탈락 전략 | 사전 고정 평가 기준 충족 |
| P4 | Buzz 에이전트·토론·최종 카드·최소 화면 | 실제 요청→반론→카드·알림 | 모델·출처·유효기한 검증 |
| P5 | 모의 주문 상태·대사·복구·실시간 관찰 | 기간·표본·장애 시나리오 결과 | 품질·위험·표본 조건 통과 |
| P6 | 버전 고정·백업·복구·제한 배포 준비 | 릴리스와 준비/보류 판정 | 별도 실거래 시작 결정 |
| P7 | 승인된 제한 운용·대사·평가 | 실제 운영 인수 결과 | 약정 기간·수용 조건 충족 |

P4 최소 화면은 관심 목록 등록, 후보·보유 상태, 결정 카드, 데이터 시각, 운용 모드와 중단 상태다.
UI 기술은 P0에서 확정한다. 배포 위치·관심 종목 등 후속 전제의 시점은 docs/evidence/P0/readiness.md 정본을 따른다.
개인 거래 화면은 공개 Pages에 배포하지 않는다.
P5의 20 거래일·100회 표본은 최소 관찰 목표다. 표본을 채우려고 불필요한 거래를 만들지 않는다.
표본이 부족하면 연장하고 성과가 부족하면 연구로 돌아간다. 개발 속도로 관찰 기간을 대체하지 않는다.
관찰 중에는 독립적인 문서·복구·보안 작업을 수행할 수 있다.

## 7. 전체 완료 기준

- 개발 완료: 요구사항별 구현·테스트·설치·문서·백업·복구가 확인된 릴리스.
- 모의 검증 완료: 실시간 모의 환경에서 사전 정의한 기간·표본·성능·운영 기준 통과.
- 실전 운용 인수 완료: 별도 승인된 제한 운용에서 실제 주문·대사·중단·복구와 결과 확인.

예측 우위가 부족하면 소프트웨어 개발은 완료해도 실전 운용은 보류한다.
수익 보장이나 매일 이익은 완료 조건이 아니다. P7 이후 개선은 새 버그·전략 변경 이슈로 관리한다.

## 8. 중단·재개 방법

재개 시 읽는 순서는 승인된 main의 README/실행 지침 → STATE → 단계 이슈와 승인 대상 → PR/CI/리뷰 → 관련 설계·테스트다.
대화 전체를 재독하거나 매번 새 계획을 만들지 않는다. 첫 미완료 수용 조건부터 이어간다.
기록이 충돌하면 최신 명시적 사용자 결정을 확인하고 실제 원격 SHA·검사 결과와 대조한다.
미커밋 변경·다른 작업자·활성 실행을 확인한다. 같은 작업에 실행자가 있으면 중복 시작하지 않는다.
GitHub 조회 실패 시 새 merge·배포·승격은 보류한다. 승인된 로컬 구현은 `pending_sync`로 진행할 수 있다.
동기화 후에만 다음 단계로 승격한다. timeout 이후 생성 요청은 재전송 전에 원격 생성 여부를 조회한다.

중단 직전에 작업 ID·SHA·완료 검사·미해결·다음 행동·실행 중 세션을 기록한다.

재개 요청 예시:

> krdn/gon-stock의 승인된 실행 제안, STATE, 현재 단계 이슈와 열린 PR을 읽어라.
> 최신 승인 범위의 첫 미완료 작업부터 이어가고 결과·검사·차단·다음 행동을 저장하라.
> 이미 검증한 일을 반복하지 말고 실거래 전환은 별도 승인 없이 실행하지 마라.

중단 요청 예시:

> 개발을 중단하고 현재 변경·검증·다음 행동을 GitHub에 저장해라.

개발 중단과 거래 서비스 중단은 다르다. 미체결 취소·포지션 처리는 별도 운용 명령으로 구분한다.

## 9. 지속 실행과 CI

초기 실행기는 현재 Codex 세션이다. 세션 종료 후 자동으로 새 실행이 이어진다고 보장하지 않는다.
사용자가 재개 요청하면 기록을 읽어 이어간다. GitHub 저장만으로 무인 실행이 생기지 않는다.
장기 무인 실행은 작업 잠금·중복 방지·timeout·반복 실패 중단·호출 예산·정지 신호를 갖춘 감독 실행기로 별도 설계한다.

| 실행 장소 | 역할 | 제외 |
| --- | --- | --- |
| GitHub Actions | 문서·형식·테스트·빌드·익명 artifact | 실계좌 키·시세 원문·거래 주문 |
| 승인된 내부 서버 | 통합 검사·모의 운용·프록시 연결 | 공개 PR 코드를 인증 환경에서 자동 실행 |
| Buzz | 연구·반론·최종 결정·장애 알림 | 채팅을 직접 주문 명령으로 실행 |

공개 CI는 최소 권한의 GitHub 호스팅 실행기로 시작한다.
금융·프록시 통합 검사는 승인된 SHA를 내부에서 실행하고 정제 결과만 게시한다.
공개 repo의 외부 PR에 내부 서버의 상주 self-hosted runner를 바로 연결하지 않는다.
artifact에는 보관 기한이 있으므로 수용 근거 요약·SHA·해시는 저장소에 보존한다.
개인 원문은 보호된 별도 저장소에서 보관·백업한다. 비밀값은 Actions 로그 마스킹에만 의존하지 않는다.

## 10. 모델·pane·리뷰

총괄 Astra 후보, 리뷰 Fable 5.2 고정, 독립 리서치는 필요한 때 Argon 후보를 평가한다.
제품 리서치 호출은 지정 프록시를 사용한다. 개발 리뷰는 후속 사용자 지시에 따라 로컬 Claude CLI를 사용한다.
요청/반환 모델·입력 SHA·지연·실패를 기록한다.
반환 모델 문자열은 프록시의 보고다. alias 실제 매핑까지 확인하고 검증 수준을 명시한다.
Fable 실패는 미완료다. 다른 모델로 통과 처리하지 않으며 해당 변경의 최종 수용을 보류한다.
리뷰를 기다리는 동안 무관한 준비 작업은 계속할 수 있다.
리서치·리뷰는 현재 터미널의 별도 pane을 우선한다. 제어·출력 회수가 확인돼야 실제 pane 실행으로 기록한다.
동시 작업은 총괄 1개와 독립 조사/리뷰 최대 2개로 제안하며 파일 책임을 나눈다.
pane 사용 허용을 새 도구 설치나 터미널 설정 변경 승인으로 확대하지 않는다.

## 11. 단계 결과 양식

```text
단계 / 이슈 / 범위 버전:
대상 commit / 데이터 버전 / 요청·반환 모델:
변경한 동작과 산출물:
수용 기준별 PASS·FAIL·NOT_RUN / 근거 URL:
Fable 지적과 처리:
개인정보 제거 / 알려진 한계:
상태: 구현 완료 / 검증 대기 / 직접 검토 대기 / 위임 수용 / 차단
다음 행동 / 담당 / 재개 조건:
```

CI PASS·HTTP 200·파일 생성은 각각의 사실만 증명한다. 시세 수신·체결·복구는 실행 근거가 별도로 필요하다.

## 12. 승인 후 첫 행동

현재 설계 초안 main, 이슈 #1, Project #19, Discussion #2, draft PR #3이 있다.
본 제안은 승인되었고 PR에서 변경 이력을 보존한다. 단계 이슈 등록 자체는 실행 증거가 아니다.
CI는 준비 PR #13에서 검사 통과를 확인했으며 통합 상태는 해당 PR과 STATE를 따른다.
Wiki 첫 페이지·branch 보호·감독 실행기는 별도 적용 상태를 확인한다.

1. 실제 승인 답변과 대상 제안 revision을 총괄 이슈에 기록한다.
2. PR #3과 본 제안의 미결정 사항을 검토·검사 후 통합한다.
3. P0에서 승인 범위에 맞는 진입 지침·최소 CI·Project 필드·보호 설정을 구성한다.
4. Fable 실제 호출과 대상 시장을 확정하고 관심 종목·운영 환경의 후속 검증 시점을 readiness.md에 연결한다.
5. P0 조건 충족 후 P1 읽기 전용 연결을 시작한다.

다음은 최초 제안의 승인 문구 예시다. 실제 답변은 위 승인 기록에 보존한다:

> execution-v1의 B 방식을 승인한다. P0~P4 개발과 P5 모의·shadow 검증을 단계별로 진행하라.
> 범위 내 구현·검사·Fable 5.2 리뷰·PR·검사 통과 후 merge·기록 갱신을 위임한다.
> 단계 결과는 보고하고 범위 변경·외부 계약·권한 확대·실거래 전환은 별도로 확인하라.

각 단계 결과를 직접 검토하려면 B 대신 A를 선택한다.
