# 구현 순서와 검증 기준

[설계](../architecture/trading-system.md) · [근거](../research/evidence.md)

수익 보장 대신 데이터 신뢰성, 손실 제한, 검증된 신호, 주문 정확성을 순서대로 증명한다.
기간만 채워 실거래로 넘어가지 않는다. 단계마다 결과·미검증·다음 조건을 기록한다.

| 단계 | 산출물 | 통과 조건 |
| --- | --- | --- |
| P0 설계 | 설계, 위험 설정, GitHub 기록 | [전제·이월 기준표](../evidence/P0/readiness.md)의 P0 조건과 Fable 리뷰·실제 모델 확인 |
| P1 읽기 전용 연결 | 키움 국내·미국 조회, 프록시 모델 확인 | 실제 타임스탬프·호가·잔고 읽기, 비밀값 비노출, 주문 호출 0 |
| P2 기록과 재생 | 종목 등록, 이벤트 저장, 데이터 품질 보고 | 중복·누락·역순·휴장·서머타임·기업행동 재현 |
| P3 기준 전략 | 비용 포함 백테스트, 확률 보정 | 미사용 평가 구간, 누출 검사, 비용 스트레스, 표본 불확실성 보고 |
| P4 Buzz 연결 | 세 채널과 역할별 에이전트 | 같은 채널에서 요청→반론→결정 카드 확인, 실제 모델·산출물 연결 |
| P5 모의·shadow | 실시간 전략과 주문 상태 머신 | 최소 20 거래일 관찰, 목표 100회 이상 체결 표본; 미달이면 연장 |
| P6 제한 실거래 준비 | 동결 버전, 복구 절차, 위험 설정 | 모의와 실전 차이 정리, 장애 재현 통과, 사용자 실거래 시작 결정 |
| P7 제한 자동 운용 | 독립 실행 서비스, 사후 평가 | 손실·노출 한도 준수, 일별 대사, 무단 전략 변경 0 |

20일·100회는 관찰 최소 목표이며 통계적 유효성이나 수익성을 보장하지 않는다.
양의 순기대값과 불확실성, 손실 한도, 거래 국면을 함께 판단한다. 증거가 부족하면 실거래로 승격하지 않는다.
확률의 신뢰구간과 전략 선택 편향을 고려한 평가 방법·판정 기준은 P3 실행 전에 고정한다.

필수 장애 시나리오는 주문 응답 유실, 부분 체결 후 재시작, 중복 신호,
취소와 체결의 경합, 환율 누락, 시세 지연, 프록시 중단, Buzz 단절, DB 중단, 일일 한도 도달이다.
모의 시스템에서 통과하더라도 실제 체결 품질과 손실 상한을 증명하지는 못한다.

개발은 이슈→목적별 branch→PR→Fable 5.2 리뷰→해당 SHA 검사→merge 순서다.
기능·설계·위험 규칙 변경에는 리뷰가 필수다. 사소한 문서·설정만 리뷰 예외로 기록한다.
현재 리뷰 경로는 사용자 지정 로컬 Claude CLI이며 제품의 리서치 프록시와 구분한다.
LLM 리뷰가 실패하면 실패를 기록하고 다른 모델의 승인으로 바꾸지 않는다.
데이터·시세 계약과 운영 모델 접근을 확인하기 전 유료 가입이나 상시 실행을 시작하지 않는다.

우선 구현 파일 구조는 다음과 같이 계획한다. 아직 생성된 구현 파일을 뜻하지 않는다.

```text
src/gon_stock/
  market_data/       # 수집·정규화·신선도 검사
  research/          # 프록시 호출·근거·구조화 결과
  strategies/        # 버전 고정 신호
  risk/              # 수량·노출·손실 제한
  execution/         # 주문 상태·중복 방지·대사
  integrations/      # Buzz·공개 요약
tests/               # 시계열·주문 장애 시나리오
docs/                # 공개 설계와 검증
.private/            # Git에서 제외한 사용자 운영 설정
```
